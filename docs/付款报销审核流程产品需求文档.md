## 2. 需求概述

### 2.1 需求来源与本阶段定位

本需求核心是新增两类申请模块与配套的校验、审批、打款、补传链路：

- 新增功能模块：报销申请（发票金额≥报销金额）、付款申请（没有发票或者发票不足）。
- 配套能力：发票校验（真伪、重复上传）、多级审批流程（管理员可配置审批层级与审批人，按金额触发，通过/驳回）、上传发票、状态同步、申请记录「再次申请」。
- 流程版本：本需求给出两套流程——报销流程（一）审核版、报销流程（二）预算版。

本阶段定位：形成一份可直接评审、可供产品研发/设计/测试落地的 PRD，明确各端侧页面与入口、关键交互步骤、状态流转与分支条件、提示文案，并将落地必需的全部内容统一编号化。

本阶段可交付目标：形成一份完整覆盖两类申请、发票校验、多级审批、两套流程全链路的 PRD，使设计、开发、测试、运营明确推进边界。

### 2.2 本次新增功能模块概览

| 新增功能模块 | 适用条件       | 核心差异                              |
| ------ | ---------- | --------------------------------- |
| 报销申请   | 发票金额≥报销金额  | 必须先校验发票，发票金额达标方可进入审批/预算判定。        |
| 付款申请   | 没有发票或者发票不足 | 审批通过后仍保留「待补传发票」状态，需员工后续补传发票并重新校验。 |

两类申请共用同一套发票校验、审批层级与状态体系；提交字段完全一致（见 4.2.2）。区别在于报销申请对发票金额达标有强前置约束，付款申请允许发票缺失/不足并以补传闭环收口。

### 3.3 双端提交差异

员工提交报销单/付款申请在**职喜智能体小程序 与 分后台 双端均支持**，两端需满足一致性要求：

| 维度   | 职喜智能体小程序                           | 分后台                    | 一致性要求                    |
| ---- | ---------------------------------- | ---------------------- | ------------------------ |
| 提交字段 | 报销申请见 4.2.1；付款申请与报销申请完全一致（见 4.2.2） | 同左                     | 同一字段集、同一校验规则             |
| 发票上传 | 拍照/相册、多张、PDF/图片                    | 同左                     | 同一上传能力与格式限制              |
| 校验结果 | 发票真伪、重复校验、金额比对提示一致                 | 同左                     | 提示文案一致                   |
| 补传发票 | 支持（见 4.7）                          | 支持（见 4.7）              | 所有支持提交申请的端侧均需实现，双端补传能力一致 |
| 状态展示 | 员工可查看本人工单状态                        | 管理员可查看名下申请状态           | 状态名称一致（统一「待审核」等，见 4.6.1） |
| 差异   | 面向员工/申请人及审批人，以本人相关申请为范围；提供再次申请     | 面向管理员/代提交，含审核流程配置与异常视图 | 差异仅在使用者与可见范围             |

双端提交维度按同一字段集与校验规则执行：报销申请与付款申请字段一致（见 4.2.1、4.2.2）；双端提交权限校验遵循原有角色功能规则。本需求未涉及申请草稿/暂存，本版不额外引入草稿/暂存功能。（TBD-04 已关闭）

### 3.5 流程版本选择机制

**关键结论（已确认）：** 职喜智能体小程序 / 分后台用户发起申请时走「审核版」还是「预算版」，由**总后台对账号的配置（账号配置）**决定。即：具体申请流程走「预算」还是「审核」分支，完全由总后台对对应账号的配置决定。

- 「账号配置」= 总后台**唯一**能力，用于配置账号的报销类型，可选值为「预算」「审核」；二者是该配置项下的可选字段值，不是独立的端侧能力。
- 选择「预算」→ 该账号的报销申请与付款申请走预算版（预算额度来源见 4.11）。
- 选择「审核」→ 该账号的报销申请与付款申请走审核版。

该关系为已确认结论，不作为待确认项。同一账号在配置生效后，其报销申请与付款申请均按被选定的流程版本流转。

预算额度无需在总后台配置：总后台暂不新增预算额度的配置粒度与判定口径功能，预算额度通过表单项（法人主体、成本类型、费用名称）关联自动带出，该业务逻辑已在现有系统中实现（见 4.11）。（TBD-07 已关闭）

### 4.2 员工申请提交：报销申请与付款申请

#### 4.2.1 报销申请提交字段

| 序号  | 字段名称    | 说明                    |

| 2   | 成本类型    | 费用所属成本类型              |
| 3   | 费用名称    | 报销费用名称                |
| 4   | 收款单位    | 收款方名称                 |
| 5   | 收款单位所属行 | 收款单位开户所属银行            |

字段取值来源与数据字典（法人主体、成本类型等是否固定枚举、由何处维护），参考现有原项目中的对应字段规范执行。（TBD-19 已关闭）

#### 4.2.2 付款申请提交字段

付款申请的提交维度字段规则与报销申请**完全保持一致**：与 4.2.1 所列 9 项字段（法人主体、成本类型、费用名称、收款单位、收款单位所属行、收款单位卡号、费用用途、备注、报销金额）共用同一字段集、同一校验规则。

付款申请同样支持上传发票（发票不足或缺失场景），上传能力见 4.5。（TBD-04 已关闭）

#### 4.2.3 提交交互（双端）

1. 员工在职喜智能体小程序或分后台选择「报销申请」或「付款申请」入口。
2. 按对应字段集填写内容（两类申请字段一致，见 4.2.1、4.2.2）。
3. 上传发票（报销申请为必需强校验；付款申请允许缺失，见 4.3、4.7）。
4. 提交后由系统执行发票识别与校验；校验通过按总后台账号配置所选定的流程版本流转，校验不通过按 4.3 分支处理。

本需求未涉及申请草稿/暂存，本版不额外引入草稿/暂存功能；双端提交遵循同一字段集与校验规则（见 3.3）。

### 4.3 发票识别与校验

#### 4.3.1 提取字段（严格限定）

发票识别提取的校验字段**仅限以下两项**，不得使用其他字段：

| 序号  | 字段名称   | 用途                     |
| --- | ------ | ---------------------- |
| 1   | 发票号码   | 发票真伪校验、重复上传校验          |
| 2   | 价税合计金额 | 与报销金额比对（判断发票金额是否≥报销金额） |

#### 4.3.2 识别失败处理与提示文案

发票识别依赖第三方识别插件的回调能力（识别结果通过插件回调返回）。（TBD-13 已关闭）

- 当出现**发票识别失败**场景时，统一提示用户「再次上传即可」。
- 识别失败的场景**直接认定为未上传发票**，按「无发票」情形处理（即进入 4.3.5 的退回分支）。

（TBD-12 已关闭）

#### 4.3.3 校验项一：发票真伪校验

系统在员工上传发票后，以发票号码为校验依据发起**发票真伪校验**；真伪校验能力由第三方识别插件回调提供（见 4.3.2）。

真伪校验失败的提示与处置遵循 4.3.2：统一提示用户「再次上传即可」，识别失败直接认定为未上传发票。（TBD-12 已关闭）

#### 4.3.4 校验项二：重复上传校验

系统在员工上传发票后，以发票号码为比对依据判断该发票是否已被上传过，即**重复上传校验**。

重复上传校验失败的提示与处置遵循 4.3.2：统一提示用户「再次上传即可」，识别失败直接认定为未上传发票。（TBD-12 已关闭）

#### 4.3.5 校验项三：金额比对与退回分支

以价税合计金额（发票金额）与报销金额进行比对，按流程版本给出不同提示语：

| 比对结果                     | 系统行为         | 提示语（审核版）            | 提示语（预算版）         |
| ------------------------ | ------------ | ------------------- | ---------------- |
| 发票金额 < 报销金额 或 无发票（含识别失败） | 退回流程，阻断进入审批  | 「发票金额不足，请点击付款申请，作废」 | 「发票金额不足，请点击付款申请」 |
| 发票金额 ≥ 报销金额              | 放行，进入审批/预算判定 | 无                   | 无                |

说明：审核版退回提示含「作废」，预算版退回提示**不含**「作废」，两处提示语差异须忠实保留。

**多张发票合计比对规则（本版结论）：** 当一次申请上传多张发票时，采用**合计比对**口径，即以多张发票的价税合计金额**之和**与报销金额进行比对（合计金额 ≥ 报销金额即放行，合计金额 < 报销金额或无发票则退回）；不对单张发票逐一比对。（TBD-11 已关闭）

#### 4.3.6 补传发票的重新校验

付款申请补传发票后需重新校验（发票真假、重复校验），校验规则同 4.3.2、4.3.3、4.3.4、4.3.5：发票金额 < 报销金额 或无发票 → 退回补传发票状态，员工继续上传；发票金额 ≥ 报销金额 → 校验通过，异常关闭（见 4.7）。

### 4.4 审核流程配置与多级审批流程

#### 4.4.1 审核流程配置（多级审批业务的基础依赖能力）

**功能定位：** 审核流程配置是分后台承载的一项基础配置能力，用于定义「申请提交后进入的审批链路」。它不是某一个具体审批环节的功能，而是**后续所有多级审批业务共同依赖的基础能力**——报销申请、付款申请，以及后续新增的任何多级审批业务，其审批链路均由此处的配置生成。缺少该能力，多级审批链路无从定义与流转。

**功能作用（配置内容）：**

1. **审批层级配置：** 定义审批链路由哪些审核节点组成、节点之间的先后顺序；层级数量与顺序**均可动态配置**，不预设固定层级（示例「直属主管 → 部门经理 → 总经理」仅为示例，非固定三级）。
2. **每层审批人配置：** 为每个审核节点绑定审批人（关联规则见 4.4.2）。
3. **每层触发条件配置：** 为每个审核节点设置进入条件，当前为金额触发（见 4.4.3）。

**动态配置原则：** 所有审核节点均支持动态配置，包括节点数量、节点顺序、节点审批人与节点触发条件；系统不内置固定审批节点集合，也不存在「待直属主管审核」「待部门经理审核」「待总经理审核」这类按具体层级细分的状态（全流程统一为「待审核」，见 4.6.1）。

**基础依赖关系：** 员工提交报销/付款申请 → 发票校验通过 → 依据本配置生成的审批链路进入审批（首个节点状态为「待审核」，见 4.6.1）→ 逐节点流转。因此，本能力是员工申请提交（4.2）、多级审批流程（4.4）、状态管理与流转（4.6）的前置依赖。

**端侧归属：** 配置入口与操作**仅**在分后台（对应 3.2 端侧能力归属中的「审核流程配置」）。

#### 4.4.2 审批人

每层审核节点对应审批人；各审批层级（直属主管/部门经理/总经理）的关联规则，本版暂定为「**部门 + 人员**」的绑定关联关系，即每个审核节点绑定的审批人由「部门 + 人员」共同确定。（TBD-05 已关闭）

#### 4.4.3 触发条件（金额）

审核节点可按金额设置触发条件（示例为「金额 > 5000 才进入总经理审批」）。本版结论：

- 该功能由**系统配置人员自主决定是否开启**，**默认状态为关闭**。
- 仅当功能**开启后**，才展示金额输入配置项；功能关闭时不展示金额输入配置项。
- 功能开启后的**默认阈值为 5000**。

（TBD-06 已关闭）

#### 4.4.4 审批操作

各级审批人对申请执行操作（**审核（报销、付款）申请在职喜智能体小程序与分后台双端均可执行**，操作与规则双端一致，见 3.2、3.3）：

| 操作  | 要求           | 后续                               |
| --- | ------------ | -------------------------------- |
| 通过  | 无强制填写项       | 自动流转下一节点；全部通过则流程结束               |
| 驳回  | **必须填写驳回原因** | 员工可修改后重新提交；再次提交回到审批流程**首节点**重新审批 |

驳回后员工「修改后重新提交」的进入位置为回到审批流程**首节点**（即每次驳回重提均从链路第一个审核节点重新开始流转）。（TBD-16 已关闭）

#### 4.4.5 流转规则

- 审批通过后自动流转下一节点。
- 全部节点通过则流程结束。
- 流程结束后进入「待打款」。

#### 4.4.6 数据同步

本版结论：全端侧的审核数据状态需保持**实时同步**，所有终端展示的审核状态必须**完全一致**（不区分端侧展示差异）。（TBD-08 已关闭）

| ---- | ------------- |

### 4.6 状态管理与流转

#### 4.6.1 状态清单（本版结论，名称全文唯一）

全流程状态暂定为以下 **5 种**，名称与含义全文唯一：

| 状态名称  | 含义                                  | 出现条件                                   |
| ----- | ----------------------------------- | -------------------------------------- |
| 待审核   | 申请处于审批链路中，等待当前节点审批人处理；**不区分具体审批层级** | 报销申请校验通过进入审批；或付款申请进入审批；或任一节点通过后流转至下一节点 |
| 审核退回  | 审批人驳回，退回员工修改后重新提交                   | 任一审核节点驳回并填写驳回原因                        |
| 待打款   | 全部审批通过或预算额度内直接通过，等待打款               | 流程结束                                   |
| 已打款   | 打款完成                                | 打款动作完成                                 |
| 待补传发票 | 付款申请审批通过后流程结束但仍保留的、等待员工补传发票的状态      | 付款申请审批通过（见 4.7）                        |

说明：

- 全流程不存在「待直属主管审核」「待部门经理审核」「待总经理审核」这类按具体审批层级细分的状态；按具体审批层级细分的三个审核状态在本版统一归并为「**待审核**」单一状态。（TBD-15 已关闭）
- 付款申请「待补传发票」状态的关闭（即链路中的「异常关闭」）为补传校验通过后的收口结果，不新增独立状态。「异常关闭」为链路结果描述，非独立状态项。（TBD-15 已关闭）

#### 4.6.2 状态流转与同步

- 报销申请（审核版）：提交 → 校验通过 → 待审核（首节点）→（通过）待审核（下一节点）→ … →（全部通过）流程结束 → 待打款 → 已打款。
- 报销申请（预算版）：提交 → 校验通过 → 预算判定，在额度内直接通过 → 待打款；超出额度进入多级审批：待审核 →（通过）待审核（下一节点）→（全部通过）待打款。
- 付款申请：提交 → 进入审批（或预算判定）→ 待审核 →（全部通过）流程结束（保留待补传发票状态）→ 补传 → 重新校验 → 校验通过，待补传发票状态关闭（异常关闭）。
- 员工申请报销后，需同步报销流程状态；全端侧审核数据状态实时同步、所有终端展示完全一致（见 4.4.6）。（TBD-08 已关闭）
- 各状态的通知方式：本阶段仅需实现**数据层的状态展示**；通知方式暂未确定，待后续需求明确后再进行开发。（TBD-17 已关闭）

### 4.7 补传发票链路（付款申请）

**适用范围（唯一口径）：** 补传发票功能由**所有支持提交申请的端侧**实现，即**职喜智能体小程序与分后台双端均需提供补传发票功能**。职喜智能体小程序提供补传发票入口，分后台侧同样实现同一补传能力（见 3.2、3.3）；管理侧补传状态查看归**分后台**。

链路步骤：

1. 员工提交付款申请。
2. 进入审批流程，进入「待审核」状态。
3. **生成异常统计 + 需要补传发票**（职喜智能体小程序与分后台均提供补传发票入口；分后台按状态区分展示异常，落地形态见 4.10）。
4. 逐级节点审批。
5. 审批通过。
6. 流程结束，但**保留待补传发票状态**。
7. 补传发票。
8. **重新校验**（发票真假、重复校验）：
   - 发票金额 < 报销金额 或无发票 → 退回补传发票状态，员工继续上传发票；
   - 发票金额 ≥ 报销金额 → 正常结束。
9. 校验通过 → 待补传发票状态关闭（异常关闭）。

**补传发票期限规则：** 本次需求未涉及补传发票期限要求，暂不设置相关业务期限规则。（TBD-14 已关闭）

- **「再次申请」规则（本版结论）：** 基于原表单内容进行**提交数据自动回显**，允许用户对回显内容进行**修改后重新提交**。（TBD-10 已关闭）

**检索筛选条件（本版结论）：** 申请记录列表与审核申请管理列表的检索筛选条件，暂定为以下三个维度：**状态、费用名称、申请时间**。（TBD-20 已关闭）

### 4.10 异常统计（分后台）

付款申请链路中需「生成异常统计 + 需要补传发票」。按本次澄清（用户确认，2026-10-15），「异常统计」在本版的落地形态为：**分后台侧对「需要补传发票的付款申请」按状态进行区分展示**，即按申请当前所处状态分状态归类呈现，供分后台管理员与财务/运营查看并按状态跟进补传、打款等事项。

展示所依据的区分维度即 4.6.1 状态清单（及 4.7 中付款申请相关的待补传发票状态、异常关闭），不额外引入计算口径。异常视图的检索筛选条件同 4.9（状态、费用名称、申请时间）。（TBD-20 已关闭）

**本版范围边界：** 本版「异常统计」**不含任何统计计算、数据汇总类功能**——如数量统计、金额合计、占比、趋势/报表等均不在本版范围内；仅实现按状态区分展示。

「异常统计」本身即为功能模块名称，全文含义唯一（即按状态区分展示的视图）。除本处与 6.1 已关闭项的历史记录外，正文不再以「统计视图」「统计口径」描述该功能。

（关联说明：付款申请待补传发票/异常状态的完整清单见 4.6.1 与 4.7；异常视图的筛选与检索维度见 4.9；原 TBD-09（异常统计相关待确认项）已随本次澄清关闭，见 6.1、7.1。）

### 4.11 总后台：账号配置（账号的报销类型：预算 / 审核）

| 能力   | 作用                                           | 关联            |
| ---- | -------------------------------------------- | ------------- |
| 账号配置 | 配置账号的报销类型，可选值为「预算」「审核」；选择「预算」走预算版、选择「审核」走审核版 | 见 3.5、5.2、5.3 |

说明：总后台**仅**具备「账号配置」这一项能力；「预算」「审核」是该配置项下的**可选字段值**，不是独立的端侧能力。具体申请流程走「预算」还是「审核」分支，完全由总后台对对应账号的配置决定（见 3.5）。

**预算额度规则（本版结论）：** 总后台暂**不新增**预算额度的配置粒度与判定口径功能；预算额度通过表单项（**法人主体、成本类型、费用名称**）关联自动带出，该业务逻辑已在现有系统中实现，本版仅作补充说明。（TBD-07 已关闭）

**角色权限规则（本版结论）：** 分后台与总后台的角色权限，按对应业务场景匹配对应菜单即可，整体规则与原有角色功能保持一致（见 3.2、3.4）。（TBD-18 已关闭）

**边界声明：** 总后台仅包含上述一项能力（账号配置），提交/审核（报销、付款）申请、审核流程配置（审批层级/审批人/触发条件）、审核申请管理、异常统计等功能均在分后台或职喜智能体小程序，不在总后台描述。

## 5. 业务流程

### 5.1 报销流程（一）审核版

#### 5.1.1 报销申请（发票金额≥报销金额）流程图

```
报销申请（发票金额≥报销金额）
员工提交报销单
        ↓
系统自动校验发票 → 发票金额<报销金额 或 无发票 → 退回流程（系统提示：发票金额不足，请点击付款申请，作废）
        ↓
发票金额≥报销金额
        ↓
进入审批流（逐级领导审批，各节点状态统一为「待审核」）
        ↓
审批通过
        ↓
流程结束 → 待打款
```

要点：审核版退回提示为「发票金额不足，请点击付款申请，作废」（含「作废」）；校验通过后进入逐级领导审批，各审核节点状态统一为「待审核」；审批通过后流程结束进入待打款。

#### 5.1.2 付款申请（没有发票或者发票不足）流程图

```
付款申请（没有发票或者发票不足）
员工提交付款申请
        ↓
进入审批流程（各节点状态统一为「待审核」）
生成异常统计 + 需要补传发票（职喜智能体小程序与分后台均提供补传发票入口，分后台按状态区分展示）
        ↓
逐级领导审批
        ↓
审批通过
        ↓
流程结束（但保留待补传发票状态）
        ↓
补传发票
        ↓
重新校验（发票真假、重复校验，发票金额<报销金额 或 无发票 → 退回补传发票状态，继续上传发票，发票金额≥报销金额 正常结束）
        ↓
校验通过
        ↓
异常关闭
```

要点：付款申请审批通过后流程结束但仍保留「待补传发票状态」；补传发票功能在职喜智能体小程序与分后台**双端均需实现**（所有支持提交申请的端侧，见 3.2、4.7）；补传后重新校验，校验通过则异常关闭。

### 5.3 流程版本选择机制说明

- 走审核版还是预算版，由总后台「账号配置」（配置账号的报销类型：预算 / 审核）决定；该配置为总后台唯一能力，「预算」「审核」是其可选字段值（见 3.5、4.11）。
- 预算版的两条分支（在预算额度内 → 直接通过 → 待打款；超出预算额度 → 进入多级审批流程 → 审批通过 → 待打款）依据账号配置选择「预算」后的额度判定（见 3.5、4.11）；预算额度通过表单项（法人主体、成本类型、费用名称）关联自动带出，已在现有系统实现（TBD-07 已关闭）。
- 两套流程的报销申请退回提示语不同，须忠实保留（见 4.3.5）。

1. 线下沟通取得结论。

3. 回填正文，替换对应内联标识（改为已确认表述并附「（TBD-xx 已关闭）」）。
4. 在第 6.1 节清单中标注该项已关闭，并注明关闭日期与结论来源。
5. 在 7.1 节新增版本行记录变更。
6. 通知第 3.4 节全部角色完成重新对齐。

编号一经分配不再复用；已关闭项保留编号与结论，便于追溯。
