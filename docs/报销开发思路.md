# 费用报销开发思路文档

> 依据：《报销流程开发文档.md》（v1.5）全部内容梳理而成。本文件是**开发思路闭环 + 快速定位排查手册**，不重复设计细节，只回答三个问题：业务链路怎么跑通（思路闭环）、改动/排查时去哪看（快速定位）、容易踩的坑在哪（风险清单）。

---

## 0. 一句话总览

新增一个独立微服务 `LZ.Reimbursement.API`（共用财务库 `LZ_Finance`），承载**报销申请 / 付款申请**两类单据的全生命周期：提交 → 发票三验（识别+验真+查重）→ 流程版本判定（审核版/预算版）→ 动态多级审批 → 财务打款 →（付款申请专属）待补传发票闭环；配套**部门管理（`LZ.Basic.API`）**与**报销预算模块（`FIN_Rembi_*` 四表）**使业务链条闭环。

---

## 1. 业务链路全景（思路闭环主图）

```text
[总后台] 账号配置(审核/预算) ──────────────┐
                                          ▼
[分后台·部门管理(LZ.Basic.API)] 部门树 + 是否开启预算(Enabled)
                                          │
   提交人(小程序/分后台)                   ▼
        │ 9 项字段 + 发票 ──► ① 发票三验(合计比对)
        │                        ├─ 不通过 → 退回(提示语分版本)
        │                        └─ 通过 ──► ② 流程版本判定
        │                                        │  部门Enabled优先 > 账号配置
        │                              ┌─────────┴──────────┐
        │                          审核版                  预算版
        │                              │                    │ 预算内→直接放行
        │                              ▼                    ▼ 超预算→进审批
        │                        ③ 动态多级审批(首节点「待审核」)
        │                          ├─ 驳回(原因必填) → 修改重提回首节点
        │                          └─ 全部通过 → ④ 财务打款 → 已打款
        │                                        │
        └── 付款申请 ─────────────────────────────► ⑤ 待补传发票(补传→重验→异常关闭)
```

**闭环自检点**（链路任意一处断掉，按此表找位置）：

| 环节 | 关键产物 | 断点排查入口 |
| --- | --- | --- |
| 发票三验 | `FIN_Reimb_InvoiceUpload`（全部尝试）+ `FIN_Reimb_InvoicePool`（成功入池） | 识别失败≠未上传；只有入池发票才参与合计比对 |
| 版本判定 | 提交时固化 `FIN_Reimb_Apply.FlowType` 快照 | 判定发生在提交时，配置后改不影响在途单 |
| 审批 | `FIN_Reimb_ApprovalInstance`（RoundNo 轮次）+ `FIN_Reimb_ApprovalRecord`（节点流水） | 驳回重提 = 新轮次，旧轮次实例保留只读 |
| 打款 | `FIN_Reimb_PaymentOrder`（幂等锁） | 打款单与申请 1:0..1，重放不会重复打款 |
| 补传 | `FIN_Reimb_PaymentException`（待补传状态机） | 异常关闭 = 补传校验通过，非独立状态 |

## 2. 端侧与服务归属（谁改哪里的代码）

| 能力 | 承载服务 | 库 | 备注 |
| --- | --- | --- | --- |
| 提交/审批/打款/补传/异常/流程配置 | `LZ.Reimbursement.API`（新增） | `LZ_Finance` | 本开发主体 |
| 报销预算四表 CRUD/额度 | `LZ.Reimbursement.API`（`RembiBudget*` 控制器/服务，第 14 章） | `LZ_Finance` | 表 `FIN_Rembi_*`，实体 `RembiBudget*` |
| 部门树/部门预算开关 | `LZ.Basic.API`（`DepartmentController`，第 13 章） | `LZ_Saas` 主库（`SYS_Department`，`Tenant="Main"`） | 跨服务经 `IHttpService.GetAsync<T>(ServiceNames.BasicService, "/api/Department/...")`，参照 `FinanceOtherService` 既有范式 |
| 账号配置 | 总后台（`LZ.Reimbursement.API` 暴露 `/admin/account-configs`） | `LZ_Finance` | 总后台唯一能力 |

**跨库铁律**：`FIN_Rembi_*`（`LZ_Finance`）与 `SYS_Department`（`LZ_Saas`）之间**没有外键**，`PartnerGID = DeptGID` 是逻辑关联；部门名称等展示字段在写入时**快照冗余**进预算表（`SysDepartmentName` 等），展示不跨服务联查。

## 4. 快速定位地图（现象 → 去哪看）

### 4.1 按表定位（数据问题）

| 表 | 管什么 | 常见问题落点 |
| --- | --- | --- |
| `FIN_Reimb_Apply` | 单据主表（9 字段、状态、FlowType 快照） | 单据状态不对 → 先看 `ApplyStatus` + `CurrentApprovalInstanceId` |
| `FIN_Reimb_InvoiceUpload` | 发票上传**全部尝试**（含失败） | "发票识别失败"类投诉都在这里，`SourceUploadId` 关联入池 |
| `FIN_Reimb_InvoicePool` | 成功发票全局防重池 | "同一张发票被用了两次" → 查池内 `InvoiceNumber` 是否存在 |
| `FIN_Reimb_ApprovalInstance` | 审批轮次（RoundNo） | "驳回后重新提交没从头审" → 查是否新开了 RoundNo |
| `FIN_Reimb_BudgetReservation` | 预算调用审计流水 | "预算锁了没释放" → 查流水状态 + `ExternalRequestNo` 幂等 |
| `FIN_Reimb_PaymentException` | 待补传异常 | "补传了状态没关" → 查 `Reevaluate` 后状态与校验结果 |
| `FIN_Rembi__BudgetManage` | 预算额度（总/锁/用/可用） | "可用额度不对" → 校验 `Available = Total - Lock - Used` 等式 |

### 4.2 按服务定位（链路问题）

| 现象 | 第一落点 | 其次 |
| --- | --- | --- |
| 提交报 `REIMBURSEMENT_ACCOUNT_CONFIG_NOT_FOUND` | 总后台账号配置（`FIN_Reimb_AccountConfig`） | 该账号 FlowType 是否停用（`IsEnabled`） |
| 审批点不动 | `FIN_Reimb_ApprovalRecord` 当前节点 + 操作人是否 = 节点审批人（部门+人员绑定） | 403 `REIMBURSEMENT_APPROVAL_NOT_CURRENT_APPROVER` |
| 预算直接放行但不应放行 | 15.3.7 版本判定顺序：部门 `Enabled` 是否被误开 | `FIN_Reimb_BudgetReservation` 里 `DirectlyPass` 快照 |
| 部门改动没生效 | 报销侧部门缓存 TTL ≤ 5 分钟（`reimb:dept:{companyID}:{deptGid}`） | 清缓存/等 TTL，再看 Basic 服务日志 |
| 打款重复 | 打款单幂等键（`ApplyNo`/`ExternalRequestNo`） | 8.5 节事务边界：打款与回写 `UsedAmount` 同事务 |

### 4.3 按状态定位（状态机问题）

主状态机只有 5 态（4.6.1 全文唯一口径）：`待审核(10) → 审核退回(20) → 待打款(30) → 已打款(40)`，付款申请另有 `待补传发票`（补传维度，独立小状态机见 9.5）。**禁止**按审批层级细分状态（无"待主管审/待经理审"）。状态与可执行操作矩阵见 9.6 节——排查"某按钮该不该出现"直接查这张表。

## 6. 风险与易错点清单（修改前先读）

1. **主键陷阱**：`FIN_Reimb_*` 表主键是 `ReimbGuid`（唯一约束），`Id` 只是标识列；**但** `FIN_Rembi_*` 与 `SYS_Department` 沿用原结构（`ID`/`DeptGID` 主键）——写代码时别把 ReimbGuid 套到这两组表上（4.1「既有表映射例外」）。
2. **跨库无事务**：报销提交（`LZ_Finance`）与部门开关（`LZ_Saas`）不在一个库，**禁止跨库事务**；部门数据走 HTTP + 缓存 + 降级（2 章铁律、15.3.7）。
3. **预算并发**：`FIN_Rembi_*` 无 `RowVersion`，额度扣减用 CAS（旧值条件更新）或 `UPDLOCK`，别自己加列（14.7 第 4 条 + 11.11 停止条件 6）。
4. **在途单不受新配置影响**：审批流程配置发布后旧版本停用，但**在途实例引用旧版本**（7.4.3）；同理 `FlowType` 是提交时快照。排查"配置改了流程没变"先确认是在途单还是新单。
5. **再次申请 ≠ 补传**：`POST /applications/resubmit`（无票重提，发票只读不重验）与 `POST /applications/{id}/invoices/supplement`（补传+重验）是两条不同接口，15.2.3/15.2.4 已分开定义。
6. **双端提交一致性**：小程序与分后台提交字段集/校验/文案必须一致（PRD 3.3），改任一端的提示语时两端同步。
7. **停止条件（11.11）**：遇到需改部门表/预算表结构、发票插件回调字段不兼容、预算口径需要新配置粒度时——**停下找需求方/架构负责人确认**，不要自行扩展。

## 8. 验收自检（提测前过一遍）

按 10 章测试要点执行，重点回归 5 条链路：
1. 报销申请·审核版全链路（提交→三验→多级审批→打款）
2. 报销申请·预算版（预算内直接放行 + 超预算进审批两条分支）
3. 付款申请·补传闭环（通过→待补传→补传重验→异常关闭；补传不通过回到待补传）
4. 驳回-重提-回首节点（含"再次申请"无票重提）
5. 租户隔离（所有查询强制 `CompanyId`；跨服务调用携带租户上下文）

自动化测试交付清单见 10.7。
